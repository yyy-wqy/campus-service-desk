# Issue #24 取消申请、审核与待审冻结

依据 Issue #24、软件需求规格说明书 V1.0 的 FR-CAN-001～005，以及已确认的补充规则实现。接入 main 已合并的 #20 工单、#21 查询与说明、#22 受理分派和 #23 维修与确认接口。

## 业务规则

| 工单状态 | 本人取消操作 |
| --- | --- |
| 待受理 | 填写原因后自行取消，直接进入已取消 |
| 待处理、处理中 | 提交取消申请，原因选填，由管理员审核 |
| 待报修人确认 | 不提供取消，继续走已解决或未解决确认流程 |
| 已完成、已取消、不予受理 | 不允许取消或再次申请 |

- 同单同时最多一条待审申请，通过事务锁和数据库条件唯一约束保证。
- 待审使用 `cancellation_pending` 附加标记，保留主状态及当前处理人。
- 待审时冻结开始维修、更新维修进度、提交结果和确认操作。页面隐藏入口，服务在锁内读取最新状态并拒绝直接请求。
- 有权限者仍可查看和追加说明。优先级沿用 #22 规则，管理员可在待处理时调整，处理中不可调整。该规则由需求提出者于 2026-11-23 确认。
- 正常待审仅出现在待处理和处理中，不与待受理的受理、首次分派或待确认的反馈未解决重叠。异常残留待审标记时，确认接口拒绝推进。
- 只有业务管理员可审核。批准进入已取消；驳回必须填写原因，仅清除标记，主状态保持不变。
- 保留申请人、申请原因、时间、审核人、结果、审核说明、维修记录和操作历史。

## 接口与并发

- `GET/POST /tickets/<pk>/cancel/`，本人取消或申请取消。
- `GET /tickets/cancellations/`，管理员待审列表。
- `GET/POST /tickets/cancellations/<application_id>/review/`，管理员审核。
- 写接口使用 CSRF 和方法限制；权限在服务内按数据库中的当前账号状态复核。
- 取消与维修服务共用 `lock_ticket_for_workflow()`。SQLite 先取得写锁再读取；支持行锁的数据库使用 `select_for_update()`。
- 申请、审批及历史写入在同一事务中，失败全部回滚。重复申请、重复审核及旧申请页面无法处理新的申请。
- 取消和审核同时推进 `repair_version`，驳回后须重新加载详情，旧维修表单不能直接重放。
- 取消与结果提交竞争时，只有符合最终状态的一方可成功。进度或开始维修先提交时，随后可以申请取消；取消先提交后，维修动作被拒绝。
- 通用 `transition_ticket()` 不再允许直接转为已取消，避免绕过取消原因和审批记录。
